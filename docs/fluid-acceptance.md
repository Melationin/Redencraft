## 1. F-7 本轮补齐的断言

### W-06 互补共享面（B）

此前只覆盖「单侧不封整面」。本轮补上缺失的另一半，并先探测了注册表的真实碰撞盒：

| 方块 | 碰撞盒 | 单侧是否封 East 面 |
|---|---|---|
| 关闭的栅栏门 | `[0,0,6 - 16,24,10]` | 否（x 两侧空）|
| 墙柱 | `[4,0,4 - 12,24,12]` | 否（四角空）|
| 羊毛地毯 | `[0,0,0 - 16,1,16]` | 向上封 / 向下不封 |
| 完整方块 | 满立方 | 是 |

断言：单门不封；同轴双门（贡献同一条带）**仍不封**；门 + 墙柱贡献不同条带；满立方封。
**依赖缺口**：26.1 的半砖与台阶在本项目尚未注册，W-06 的砖块用例按缺口登记（测试断言它们确实不存在），未假装通过。

### 派发 trace（A + B）

F-7 要求「已消费的显式空流体刻、读到空气的陈旧刻……两者均不得写方块」。

**本轮发现并修复一个真实缺陷**：`World::tickFluidAt` 在 `expected->isEmpty() || fluidState.isEmpty()` 时直接 `return`，早于 trace 记录，因此「派发到但该格已是空气」的陈旧刻被**静默吞掉**，trace 中完全不可见。这违反 `AGENTS.md`「不得用静默成功冒充已完成」。修复后两种惰性情况都记录 `fluid_tick` / `fluid_tick_skipped`，并断言都不写方块。

### A-05 稳定窗口（B）

- **稳态类**：封闭 1 宽水槽，200 刻后 `fluidTickCount()==0`，再跑 100 刻无新刻且各格状态不变。
- **循环类**：自我重触发观察者，逐刻记录待处理方块刻数，断言窗口内上界有界（不是「队列非空即失败」）。

### 湿态与干态红石对比（B）

同一活塞夹具建两次（干 / 含水源 + 含水宿主），断言：两者**都**正常伸出并推出方块；差异在于湿态保留水与含水宿主、干态没有。差异被显式断言，而不是「两者都不崩」。

### 协议 N-01 / N-02 / N-04（B）

- **N-01**：快照区段混放纯水、流动岩浆、含水墙、干墙；冻结后再改活世界。**真正编码后逐段解码**：解析高度图、每区段的 `nonEmpty`/`fluid` 两个计数、调色板与格子值，断言四格按官方协议 ID 精确还原，且解码出的非空计数与流体计数与包头一致（非空 4、流体 3——含水宿主经官方 `state_flags` 计入流体，测试用同一标志核对而不是从方块名重推）。注意快照存内部 `BlockState::Id`，协议 ID 在编码时产生。
- **N-02**：接上生产用观察器（`blockUpdateObserver` / `blockEventObserver` / `blockUpdatesBroadcastObserver`，与 `src/net/server_main.cpp:614-632` 同构），把活塞事件安排到首个水刻到期的**同一 tick**（第 5 刻）。断言：事件确实发生在第 5 刻；该刻的广播阶段在水刻写入**之后**、方块事件**之前**（`engine.cpp:1734-1740` 的顺序）；同时解码 `block_update` 与 `section_blocks_update` 两种包，逐格断言最后一个包携带的是**当前活世界状态**；水确实到达下游格。
- **N-04**：慢会话不读包时核心流体队列仍推进到收敛，健康会话不被影响且仍可交互。**未覆盖**：服务端 `OutboundQueue` 的环/字节上限与断连策略——该层不在单元测试驱动范围内，如实登记为未覆盖。

### 协议状态回归（B）

固定导出中水/岩浆共 **32 条**完整状态：

| 流体 | 协议 ID | 档位 |
|---|---|---|
| `minecraft:water` | 86…101 | `level=0…15` |
| `minecraft:lava` | 102…117 | `level=0…15` |

`wire_tests` 双向核对 `stateId` / `stateById`，断言两个 16 条区间连续且不相交，越界 ID（真正高于整表最大 ID）与 `-1` 均被拒绝。

**变异验证**：把 32 条水/岩浆状态整体重排成从 500/600 起的连续 ID 后，`wire_tests` 失败；还原后通过。另把水全部 +1 平移，同样被拒绝。

## 4. 真实 26.1 服务端差分（D 类，已执行）

夹具：y=80、x∈[-2,6]、z=0 的封闭 1 宽水槽（地板、天花板、两侧墙、两端石块封堵）。
两端以 `setblock ... water[level=0]` 放置水源（走正常 `onPlace` 路径），随后逐刻推进。

- **原版侧**：官方 26.1 dedicated server（`server.jar` SHA-1 `3872a7f07a1a595e651aef8b058dfc2bb3772f46`），Java 26，`tick freeze` + `tick step 1`，逐刻用 `execute if block ... run say` 采样 9 个格子。
  脚本 `validation/vanilla26_1/fluid_validation.py`，原始日志 `fluid-vanilla.log`，黄金结果 `fluid-vanilla-states.json`（117 条观测）。
- **C++ 侧**：`tests/fluid_differential_probe.cpp` 用完全相同的布局顺序与采样点，`validation/vanilla26_1/fluid_differential_test.py` 做比对。

**结果：117 条观测全部一致**，包括中间格保持水源、两侧 `water1`、`water2` 对称衰减的稳态形态。

该比对已接入 CTest（`fluid_differential`），但需注意它的性质：

> 这是一条**回归钉**：它重跑 C++ 侧并与已记录的黄金结果比对，**不会重跑原版服务端**。黄金文件本身才是 D 类证据。

变异验证：把水的 `tickDelay` 从 5 改成 4，差分报出 5 处不一致（如 `T4 cell 1 cpp=water1 vanilla=air`），确认这条钉能抓到真实行为偏差。

**仍未做**：与差分夹具**匹配工作量的性能对跑**。上面只比对了行为逐刻状态，没有比较两端的耗时分布或整服吞吐。
